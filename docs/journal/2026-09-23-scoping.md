## Spec facts that shape the design

1. Protocol §2.1 lists three ways to send a query (GET, URL-encoded POST, direct
   POST). The prose is written from the client side, but the W3C test suite has
   one test per way (`query_get`, `query_post_form`, `query_post_direct`), so a
   service that rejects one of them fails a conformance test.
2. Protocol §2.1.6 and §2.1.7: a 2xx body must be a results document in the
   declared media type; a syntax error should be a 400, a failed execution a
   500. HTTP 200 with an error body (checklist B2) is a protocol violation, not
   a quirk.
3. Federated Query §4, "SERVICE Variables", is informative. An engine that
   rejects `SERVICE ?var` (checklist B4, QLever) is not violating SPARQL 1.1.
   It is a capability gap for a hub that wants to route federation.
4. The protocol test manifest has 34 tests. 14 are update tests and 6 need
   test datasets, and one sends a PUT. The remaining 13 are read-only and
   data-independent, so they can run against production endpoints. A PUT to the
   wrong URL can overwrite data on a Graph Store Protocol endpoint, so that test
   is excluded on purpose. Several tests pass `default-graph-uri` pointing at an
   external document; some engines dereference that, so the monitor drops it
   and says so.
5. Query-language compliance needs the W3C test data loaded into the store. That
   cannot be done on someone else's production endpoint, so it is an engine and
   version property, not something this monitor can measure remotely.

Consequence: reaching a checklist layer does not mean SPARQL 1.1 compliance.
Protocol conformance gets its own score next to the layer grade.

## Live observations today

KGI hub, `https://sparql.kgi.services.base4nfdi.de/api/` (QLever):

- Answers `ASK {}` through all three request forms in about 100 ms.
- Returns JSON, XML, CSV and TSV results. The Guidelines comparison table says
  QLever outputs JSON only, so that table is out of date.
- A syntax error returns HTTP 400 with a JSON body whose key is `exception`
  (useful as an engine signature). No `Server` header.
- `Accept: text/html` returns HTTP 500. HTTP semantics would call for 406.
- GET without a query returns 404, so there is no service description (the
  Service Description spec says a service SHOULD provide one).
- 403 triples, 35 `dcat:Dataset`, 31 `dcat:DataService`, the same totals as in
  July. The registry has not changed since then.

Registry records, 35 in total:

- Duplicates visible in the raw data: FactGrid as `/query/` (KGR83) and `/query`
  (KGR16); Semantic Kompakkt with and without a trailing slash (KGR51, KGR72);
  MatWerk under two hosts (KGR74, KGR34).
- Free text in `dcat:endpointURL`: GND "work in progress", DSKG "not available
  anymore". ORKG packs two URLs into one value separated by a semicolon.
- Every `dcat:endpointURL` value is an `xsd:string` literal. DCAT gives the
  property the range `rdfs:Resource`, so an IRI is expected. This is a
  registry-wide representation defect that the checklist does not list as a row.
  It gets reported once for the registry, not 31 times.
- Four records have no endpoint at all.

Ontology releases used as references for C4 and C5: NFDIcore v3.0.5
(2026-04-30), MWO v3.0.2 (2026-06-22).

## Open for human review later

- A2 (dump or API only): the checklist lists it as a defect, but the D3.1
  guidelines make SPARQL optional. Treated here as a warning, with layers B and C
  marked not applicable instead of blocked.
- URL normalisation (A7) can land on a different service on the same host. A
  normalised URL is recorded as a proposal, never as a fact about the registry.
- MatWerk is registered twice under two hosts with two different titles. No
  mechanical rule catches that; A6 will miss it unless the landing pages match.
