Query-layer monitor

Every SPARQL endpoint in the KGI knowledge graph registry, checked in the order the checklist prescribes: first whether there is a URL to query (A), then whether it speaks the protocol to an ordinary client (B), then whether what it serves can be trusted (C). A failure on one layer means the layers above it cannot be measured, and the page shows that as “not measured”, not as a failure.

What each check asks

The rows of the D2.1 checklist as the monitor implements them. Rows that gate the grade must pass (or need a look, or not apply) for a knowledge graph to climb past their layer.

Read the numbers with these in mind

  • Latency is measured from one place, the machine that ran the monitor, and includes its network path. Compare endpoints within a run, not across vantage points.
  • Scan-prone checks (B3, and graph counts for C1 and C2) are skipped on stores above 50 million triples to keep the monitor polite. They show as unknown, never as passed.
  • Several thresholds are judgement calls awaiting review: the 50 million triple gate, the 5 % tolerance in C5, the graph-name hints in C2, the table of reference releases behind C4 and C5, and treating a dump-only record (A2) as a warning because the KGI guidelines make SPARQL optional.
  • An endpoint URL found by normalisation is a proposal. It may point at a different service on the same host until someone confirms it.
  • The W3C score uses the 13 read-only tests of the SPARQL 1.1 Protocol suite. It measures protocol conformance, which is a different question from the grade.
